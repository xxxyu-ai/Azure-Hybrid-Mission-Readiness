# LAB 09b: Implement Azure Container Instances

## Task 1: Deploy an Azure Container Instance using a Docker Image

In this task, I provisioned an isolated container instance using a pre-configured Docker image. Azure Container Instances (ACI) allows for running containers without managing any underlying virtual machines, representing the "Serverless" approach to containerized workloads.

---

### Implementation Steps
1. **Container Resource Provisioning:**
   - **Resource Group:** Used `az104-rg9` for resource consistency.
   - **Container Name:** `az104-c1`.
   - **Region:** `East US`.
2. **Image Selection:**
   - **Source:** Quickstart images.
   - **Image:** `mcr.microsoft.com/azuredocs/aci-helloworld:latest` (Linux).
   - *Logic:* This standard hello-world image is used to verify container runtime and networking.
3. **Networking & Connectivity:**
   - **DNS Name Label:** Created a globally unique DNS name.
   - *Result:* The container is reachable via `[dns-name-label].eastus.azurecontainer.io` instead of just an IP address.
4. **Optimization:**
   - Disabled container instance logs for this specific lab deployment to speed up the provisioning process.
5. **Deployment:** Successfully validated and initialized the container.

## Professional Insight
- **Serverless Containers:** ACI is the fastest way to run a container in Azure. Unlike AKS (Azure Kubernetes Service), there is no cluster to manage. It is an ideal "Zero-Failure" solution for simple applications, task automation, and build jobs.
- **DNS vs. IP:** By configuring a DNS name label, we ensure that the application is accessible through a human-readable URL. This abstraction is vital because the underlying public IP address might change if the container is restarted.
- **Speed of Deployment:** Unlike a Virtual Machine that takes minutes to boot an OS, a container starts in seconds because it shares the underlying host OS kernel, making it perfect for rapid scaling and on-demand compute.

## Task 2: Test and Verify Deployment of an Azure Container Instance

In this task, I verified the accessibility of the containerized application and inspected the real-time logs generated by the container runtime. This confirms the successful end-to-end deployment and network configuration of the serverless container.

---

### Implementation Steps
1. **Connectivity Testing:**
   - Navigated to the **FQDN** (Fully Qualified Domain Name) of the container instance in a web browser.
   - **Result:** Successfully accessed the "Welcome to Azure Container Instance" landing page, confirming that Port 80 was correctly opened and the DNS label was functional.
2. **Traffic Generation:**
   - Refreshed the browser page multiple times to generate active network traffic and corresponding log entries.
3. **Log Inspection:**
   - Accessed the **Settings > Containers** blade and selected the **Logs** tab.
   - **Result:** Observed the **HTTP GET** requests being recorded in real-time. This proves the container is processing requests and the monitoring interface is correctly capturing the STDOUT/STDERR streams from the container.

## Professional Insight
- **Serverless Observability:** In a traditional VM (AZ-800/801 context), viewing web server logs would require RDP/SSH or configuring a log forwarder. With ACI, the logs are streamed directly to the Azure Portal, simplifying troubleshooting for "Zero-Failure" operations.
- **Port 80 Default:** By default, ACI exposes Port 80 for public traffic. For production workloads, we would typically place an **Azure Application Gateway** or **Azure Front Door** in front of the container to provide SSL termination and Web Application Firewall (WAF) protection.
- **Stateless Nature:** It is important to remember that these logs are ephemeral. If the container instance is deleted, these local logs are lost. For persistent logging, I would integrate the container with **Azure Monitor (Log Analytics)** to ensure long-term data retention and auditability.
